# LafazFlow full application replacement — continuation roadmap

Written 10 October 2026 for the next work session. **Plan only; no replacement delivered.** Owner approved a complete internal replacement and asked to preserve the **LafazFlow brand**, while replacing the existing recording, transcription, interface, and other internals. This roadmap supersedes an incremental fix to the current Whisper worker. See the [reported missing/invented speech incident](../../references/2026-10-08-trailing-invented-speech.md) and [task tracker](../../../tasks/todo.md).

## What we are building

Build a locally running Windows LafazFlow dictation app using a **pinned, existing Windows-capable dictation application** as its foundation. Handy v0.9.8 is the initial candidate, not a confirmed winner. Use its native capture, VAD, model lifecycle, UI, shortcut and paste pipeline as the starting point; do not wrap or quietly fall back to LafazFlow's existing WPF app, persistent Whisper worker or `whisper-cli`. Preserve the brand, local/offline voice processing, privacy, reliable capture and the daily dictate-into-any-app workflow. Double Shift is the owner's preferred default gesture; if the candidate does not support it safely, implement and validate it in the new foundation rather than transplanting the old hotkey service. A model decision is not an app decision: evaluate capture, decoding and paste separately, then together.

Avoid claiming that an upstream application is perfect or that a new model fixes lost audio. The replacement must earn its place against the owner's failure recordings and real microphone use. Keep the currently installed app usable until the new one is proved and independently installed. No public release is authorized by this plan.

## Stage 1 — establish a trustworthy replacement baseline

1. Verify the pinned checkout, SDK/compiler prerequisites, disk space, model download source and license. Keep all downloads and private test results under an ignored local location. Use Handy's own model manager to download/check V3 against the catalog hash; preserve the actual hash, model files and runtime configuration in private notes. Do not install the upstream-branded app as LafazFlow.
2. Try to correlate an affected recording with capture/paste time and installed version in the local logs. If it was not retained, record a fresh *opt-in* failure example. Label ground truth by listening locally, not by treating the old transcript as truth. Include immediate opening words; weak/quiet endings; intentionally spoken "thank you"; trailing silence/noise; short and long pauses; the reported missing-middle loop; short silence-only recordings; long dictation and rapid consecutive dictations. Keep audio, transcripts, prompts, endpoint identifiers and any personal data outside Git.
3. Replay the same 16 kHz mono files through the current installed engine and V3 via the upstream **headless file** entry point. Record model identity, backend, settings, load time, inference time, text, first/middle/last-word preservation, deletions, invented words, empty results and errors. Separate transcription failures from capture/VAD failures; replay cannot prove live microphone capture. Compare V2 on the **same** clips only if V3 shows omissions, hallucinations, language drift or unacceptable latency. Test English-only and, if required, Malay code-switching separately; V3 does not claim Malay support.
4. **Exit gate:** an auditable local table of matched audio results and explicit open problems. If V3 fails the owner's primary trust cases, do not promote it because it is newer; investigate alternative engines/models already supported by the candidate or reconsider the foundation. A vendor leaderboard alone cannot pass this gate.

## Stage 2 — make a LafazFlow-owned, buildable application

1. Choose a durable source location/repository for the replacement instead of making the temporary upstream checkout the only source of truth. Record the upstream base revision, keep MIT license/copyright attribution, inventory third-party models/assets, and preserve a reproducible dependency lock. A public source migration or new repo setup must be an explicit implementation step; **this planning commit does not copy the upstream source**. Do not delete the legacy repo or private owner data in the migration.
2. Remove/replace upstream-controlled identity everywhere: executable/product/bundle name, Tauri application identifier and store paths, Windows installer/service/shortcut metadata, tray and notification labels, icons, logos, UI illustrations and copy, URLs/donation/help/update endpoint, signing command, portable marker, crash/log labels, default models/download mirrors and language strings. Replace reserved art with LafazFlow-owned artwork or original alternatives. Ensure no upstream update can silently overwrite the branded app. Preserve legitimate source attribution in notices; audit output package content, not just source strings.
3. Keep upstream-native audio/VAD and transcription settings as the first functional prototype; configure a selected, locally measured model. Preserve only genuinely requested workflow behavior. Implement double Shift as a reliable toggle if feasible on Windows, with explicit key-up/repeat/stuck-key recovery and no trigger while Shift is held. Test against typing and rapid start/stop. Do not introduce the old WPF hook to save time. Provide a visible microphone/device/recording state and an honest no-speech/error path.
4. Rebuild cleanly in Release, run upstream Rust/front-end checks, verify help/headless model listing and UI launch from a **separate development install**. Confirm the test app uses a different ID/data directory/shortcut so it cannot seize the daily app, hotkey or recordings. Roll back prototype setup on conflicts rather than uninstalling the current app.
5. **Exit gate:** reproducible LafazFlow-branded standalone Windows build from pinned source, with license/asset audit and no old LafazFlow worker/CLI loaded or packaged. A renamed upstream binary is insufficient.

## Stage 3 — verify the actual daily experience

1. In isolated trials, test native microphone capture with the owner's device, its first PCM readiness, device choice/reconnect, VAD beginning/ending boundaries, stop drain and full saved audio. Compare preview versus final; distinguish audio that was never captured from audio captured but mistranscribed. Require repeated immediate-opening and quiet-ending spoken trials plus a full-length trial; record trial counts and misses rather than claiming a guarantee from a single pass.
2. Exercise configured model and any legitimate fallback offline with network unavailable after model installation. Run short, long, silent, noisy, paused and rapid back-to-back dictations. Track inserted/extraneous words, onset/ending preservation, empty-result handling, memory/process health and stop-to-paste P50/P95. Do not recover by silently returning to the old engine.
3. Test hotkey, overlay/focus, clipboard preservation and exactly-once paste in the owner's real target apps (including browser, Cursor/VS Code integrated terminal and other daily text fields). Keep manual clipboard fallback for a missed paste. Test UI settings, model download, accessibility/keyboard navigation, failure guidance and restart/sleep/device changes.
4. **Exit gate:** the owner can complete representative live tasks without the reported trust failures across repeated trials; record settings, results and any misses. Quality must be measured, not inferred from matching a logo or passing unit tests. If it fails, continue in the isolated build and diagnose the specific capture/decoder/paste phase before a cutover.

## Stage 4 — switch the canonical LafazFlow installation

1. Archive the installed build/version, current shortcut target and private settings/recordings without putting them in Git. Plan supported settings migration (language, model, device, shortcut, vocabulary, sound, clipboard) explicitly; retain owner data and do not import secrets accidentally. Remove old engine and CLI from the **replacement package**; preserve a rollback copy of the old installation until acceptance. Update the delivery/install script to understand the new architecture rather than calling the old WPF publish routine for a Tauri build.
2. Commit **verified implementation** on `main` under the repository's owner-local rule, then run the revised owner-install script to update and launch `%LOCALAPPDATA%\Programs\LafazFlow\LafazFlow.Windows.exe` or deliberately migrate the owner's taskbar pin to an equally stable new canonical executable. Verify the actual running process path/build commit, model/backend, no old worker/CLI, hotkey and paste. Push `main` only after successful installation and validation. Do not claim this roadmap's documentation-only commit installed anything.
3. Record source commit, build identity, tests, local trial counts, owner-install status and remaining limits in the incident reference and task review. Owner acceptance is a separate check after normal use. Roll back to the saved installation if voice quality, startup, hotkey or paste regresses. Public installer/release needs its own verification and separate go-ahead.
