# Dictation invents endings and loses spoken openings

Date: 8 October 2026, Asia/Kuala_Lumpur. Status: Cutover planning after a second failure report; causes of these specific recordings not yet confirmed. No fix delivered.

Implementation handoff: [full application replacement roadmap](../superpowers/plans/2026-10-10-lafazflow-full-replacement-roadmap.md). This planning documentation is not an owner-install or a fix commit.

## Symptom and impact

The owner reported three dictated sentences today ending with an unspoken courtesy phrase, including a sentence about a Financial tab and cards. The owner also reported that a sentence starting with several spoken words was pasted with only its closing words. Both invented and missing words make pasted dictation untrustworthy. The verbatim dictations and any private audio belong outside Git.

The owner explicitly rejected further incremental repair and requested a cutover to an existing working dictation foundation, refined after adoption. Clarification: **retain the LafazFlow brand only**; replace the engine, capture, interface, and other internals. An engine-only swap or an unchanged shell does not satisfy the request.

- The running canonical executable is `%LOCALAPPDATA%\Programs\LafazFlow\LafazFlow.Windows.exe`, product version `1.1.2+158dd9e20e05cd5be681cb9a096ab34b14d4aae1`. The running worker is in the same installation. This is the build with the 7 October no-speech gate.

These records do not include dictated text, so they do **not** identify which sessions produced either reported failure. No matching retained recording or transcript has yet been identified. Neither report is a verified replay.
- Current final-worker code runs Silero once to check for **at least one** speech segment, then beam-decodes the entire original waveform, including any trailing non-speech (`native/LafazFlow.WhisperWorker/main.cpp`, `Transcribe`). Direct final CLI and CLI fallback explicitly disable VAD (`WhisperDecodeOptions.ForCompleteFinalPass`). The controller checks empty text and repetitive prompt leakage, but does not have audio-grounded protection against a short invented suffix. This is a confirmed *protection gap*, not a proven cause of the three reported occurrences.
- The previous no-speech fix [rejects entire recordings with no detected speech](2026-10-07-no-speech-hallucination.md); it does not classify the ending of a recording that contains real speech. The [long-phrase-loop fix](2026-10-07-long-dictation-phrase-loop.md) protects against another failure shape.

Private evidence location: `%LOCALAPPDATA%\LafazFlow\Logs\lafazflow.log` and, only where diagnostic retention was enabled, `%LOCALAPPDATA%\LafazFlow\Recordings`. Never put audio, transcripts, or prompts into this reference or Git.

## Reference behavior and replacement direction

At the pinned source revisions, [Handy](https://github.com/cjpais/Handy/blob/37a26fd6ab905259d66affea57fff448288ca1aa/src-tauri/src/audio_toolkit/audio/recorder.rs) drops non-speech frames when recording with VAD enabled, [VoiceInk](https://github.com/Beingpax/VoiceInk/blob/7023a6f7e16ba09c3b131fe71f8cc9e55c065f19/VoiceInk/Transcription/Whisper/LibWhisper.swift) can use decoder VAD when configured, and [FluidVoice](https://github.com/altic-dev/FluidVoice/blob/4ce0584f93efbb5240d07b5039e23b09487b6ce0/Sources/Fluid/Services/ASRService.swift) has an optional short-silence gate. These are source-observed safeguards, not proof they would handle this exact waveform. LafazFlow deliberately retains the full waveform to protect quiet words; simply removing all VAD-classified audio could regress the known long-speech/first-word issues.

The owner has superseded the proposed in-place suffix fix. [Handy](https://github.com/cjpais/Handy) is a viable **candidate** replacement foundation: its Windows-capable offline application already owns microphone capture, Silero-based filtering, speech models including Parakeet, hotkeys, and paste; its source is MIT licensed. Its latest upstream README lists Windows installation and local processing, and its Cargo manifest confirms Windows builds and speech backends. This does not yet establish parity with the owner's exact shortcut, models, microphone, target applications, or quality on this hardware. VoiceInk and FluidVoice are macOS apps at the inspected revisions; their behaviors are references but neither is an immediately runnable Windows replacement.

Evaluate a pinned Handy version on the owner's machine with a fresh local-only comparison against the current installed build. A full application fork is the working direction, pending quality verification, not a wrapper around the existing worker. Handy's MIT code can be reused with its copyright/license notice, but its [README states its name, logo, icons and brand assets are not open-source](https://github.com/cjpais/Handy/blob/main/README.md#license): replace those with LafazFlow-owned branding; do not redistribute Handy-branded assets as ours. An off-the-shelf product can have its own failure modes; no absolute claim is made that every reported waveform will be handled until the same audio is tested. Handy v0.9.8 is an available Windows x64 release (3 October 2026); its tag points to `14f6f0d31cb22a4268acfbddba3052820fd0a06e`. Verify a source-buildable replacement before migration.
